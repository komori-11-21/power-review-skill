# 《通用分析思路总文档》

> **定位（初版待迭代）**：沉淀所有鸿蒙平板功耗单通用的分析方法论，不绑定具体 `.db` 表名或某个模块历史案例。当前文档为初版通用基准，**若下文示例数值门槛与 `../assets/config/thresholds.json` 不一致，一律以 `thresholds.json` 为准**。每次审单结合 [case_knowledge_base.md](./case_knowledge_base.md) 一同使用；跑单中发现新规律或误判边界时，经确认后直接更新或追加到本文档。

## 一、真 / 模严格分层与定罪原则

1. **真实值与模拟值严禁混为一谈**：
   - **唯一硬件真实电量来源（电池真值）**：电池放电 `mAh`（或百分比 `level %`——若只能靠 `level % × 电池额定容量` 推算电流，必须标成 **`[估算值]`**）、实时电流、真实均流 $I_{\text{real}}$（`mA`）、掉电率 $R_{\text{real}}$（`%/h`）、温度（`℃`）；
   - **子表真实物理指标**：AP/子系统深睡时长占比（`%`）、持锁时长占比（`%`）、刷新率档位驻留比（`%`）、线程真实 `thread_time` 占比（`%`）、硬件 IRQ / Alarm / 无线扫描频次（`次/h`）、真实网络收发包/字节率；
   - **软件模拟估算值**：器件表、应用表里的能量数字均为软件模型估算，**只用于看内部相对占比 `Share %` 与计算模拟覆盖率**，严禁把“模拟毫安”直接当真实放电电流！
2. **软件模拟覆盖率公式**：
   - $\text{覆盖率 (\%)} = \frac{\text{SUM(全部已知硬件器件模拟能量 mAs)} / \Delta t}{I_{\text{real}}} \times 100\%$
   - **单位与防重算提醒**：计算前先将各器件表能量统一换算为 `mAs`（例如 `1 mAh = 3600 mAs`、`1 uAh = 3.6 mAs`，能量单位 `mWs/uWs` 需按电压口径折算），且不要重复累加同一器件的父子汇总行；
   - **用途**：快速划分“软件可解释功耗”与“疑似未解释耗电”；覆盖率偏低时先排查有没有缺表或单位算错，排除后再查软件盲区与外设/硬件漏电。
3. **双榜合并防漏网原则（统一 4 列表）**：
   - 入表对象 = **实测大户榜**（`>= 3%` 或 `>= 3次/h` 全收，不足则保底前 5 名） $\cup$ **对比突增榜**（`Target - Ref` 降序 Top 3），其余长尾合并为 `Others（其余 N 项合计）`。
4. **累加数用“结束减开始”，不要直接 `SUM`**：
   - 有些表里记录的是**开机以来一直往上累加的总数**（好比汽车里程表，比如累计持锁时间、累计唤醒次数、累计耗电量）。算某一段时间消耗了多少，必须用**这段结束值减去这段开始值**（中途发生重启清零要分段相减，跨时间段的时长只算落在本段里的部分），**千万不能直接把每一行加起来 `SUM`**。
5. **缺数据写“无数据”，绝不填 `0`**：
   - 如果某一项在异常段或对照 `Ref` 段里压根没采到（缺表、缺字段或这段未采集），表格里直接写 **`无数据`**，不要默认写成 `0`——否则会把“没采到”误当成“原本是 `0`、突然暴增”；只有确认完整采集且确实没发生时，才算 `0`。

## 二、第一步：先排除“用户正常重度使用”（豁免白名单）

拿到证据后先逐条对照下表。**注意：识别出用户在正常重度使用（如听歌、打游戏、传大文件），只说明主场景耗电合理，不代表整段一定没问题**——仍要顺手检查有没有与该场景无关的高耗电后台、长时间持锁或异常高频唤醒；只有同时确认“主场景合理 + 无明显无关异常拖累”，才可整段定性为 `正常耗电豁免（建议解释关闭）`（否则主场景免责，异常后台/持锁项仍需指出来继续查）。

### 1. 灭屏正常豁免场景
- **熄屏听歌 / 听书 / 语音通话**：
  - 需同时满足：`Audio`（或 `Audio + BT`）器件模拟占比高（`> 25%`）+ 音乐/听书/会议通话类应用居应用榜首位。
- **熄屏大流量真下载 / 热点共享**：
  - 需同时满足：`Wi-Fi / Modem` 器件占比高 + **真实网络吞吐量高（如 `> 100 MB/h`）**；
  - *反例严禁豁免*：若持锁占比很高但真实吞吐极低（如 `< 5 MB/h`），说明下载卡死空转，必须判定异常！
- **手写笔单次正常快充**：
  - 需同时满足：灭屏短时间内（如 `< 45 分钟`）无线充开启一次，充满即停且无反复开关/电量跳变。

### 2. 亮屏正常豁免场景
> **亮屏豁免硬前提**：全机**无关后台陪跑耗电总占比必须 `< 15%`**，且没有无关的长持锁/高频唤醒异常（若后台陪跑很高，即便前台在打游戏也需指出异常后台！）。

- **重度高帧游戏**：主流游戏类应用前台居首且持续运行时长高，`CPU/GPU/Display` 合理偏高，后台无异常偷跑；
- **视频会议 / 网课教学**：会议或教育类应用前台居首，伴随合理的外放 `Audio` 与/或前后摄 `Camera` 开启；
- **户外超高亮度使用**：屏幕平均亮度极高（如 `> 80%`）且 `Display` 耗电占绝对主导；
- **平板分屏与多窗并发办公**：需有证据表明 `>= 2` 个应用在同一时间段里**真的同时在前台跑**（例如前后台时间区间有重叠、有分屏/多窗窗口状态标记，或这段内各应用前台时长加起来明显超过切片总时长，如 `> 1.2 × Δt`）。**注意**：不能只看到 A 和 B 各自前台占比都超过 `30%` 就当成分屏，因为用户也可能是先用了半小时 A、关掉后又用了半小时 B（前后切换）。

## 三、第二步：从 `.db` 4 列对比表锁定“新嫌犯”的通用看表法则

当 `.db` 检出的问题不在旧知识库中时，按以下 4 步锁定嫌犯：

1. **先看软件模拟覆盖率（先查漏算，再分软硬边界）**：
   - 若灭屏真实均流偏高但模拟覆盖率极低（初版参考 `< 35%`），**先不要直接定论硬件漏电**——先检查是不是漏了部分硬件器件表、采集时间没对齐或单位没统一换算成 `mAs`；确认没算漏后依然偏低，才标记“存在未解释耗电”，再按 **软件监控盲区（外设复充 / 硬件底电流漏电）** 排查对应外设状态与硬件中断，或建议硬件实测。
2. **灵活解读 4 列对比表（同时兼容偶发与全程漏电）**：
   - **当参照段 `Ref` 正常低耗时**：重点看 **第 ③ 列 `对比变化 (Target - Ref)`** 抓暴增真凶（含排名第 6~10 的 `[突增入选]` 项） + **第 ① 列** 实测大户；
   - **当参照段 `Ref` 同样很高（整份 `.db` 全程漏电）或 `Ref = 无`（全库仅 1 段）时**：忽略可能接近于 0 的第 ③ 列，**直接看第 ① 列 `当前异常段实测` 中断层霸榜的对象**！
3. **跨表同名共振定罪（最硬铁证）**：
   - 只要同一个名称（包名/进程名/服务名）同时在 **2 张及以上不同维度表**（例如应用耗电 + 持锁 / CPU 线程 / Alarm / 网络包）排名前列，直接锁定为头号嫌犯。
4. **亮屏先分前后台责任**：
   - 优先计算全机亮屏后台耗电总占比：若超线（如 `> 25%`）先抓后台第 1 名陪跑者；若全在前台，再核查是否属于正常重度场景，或存在 LTPO 高刷锁死 / DSS 退化 GPU / 异常发热降频。

## 四、第三步：查日志通用破案思路（从已知到未知）

> **核心策略**：先拿 `.db` 锁定的对象查 [case_knowledge_base.md](./case_knowledge_base.md)。  
> 1) **命中老问题** $\rightarrow$ 直接按卡片“② 日志怎么看”核实；  
> 2) **遇到未知新模块** $\rightarrow$ 先看召回的**同类旧案例卡片**，提炼专家的“DUBAI $\rightarrow$ 日志”排查套路进行**照猫画虎**迁移（替换包名/锁名/关键动作重查），再借助“对比差分、包名转 PID、关键字检索、前后上下文”定位下面 5 类常见死法：

1. **思路 ①【持续占用型异常（持锁高 / 高刷锁死 / 音频或相机常开） $\rightarrow$ 查生命周期“有借无还”】**
   - 在异常时间窗开头搜该对象的申请/开启打印（如 `Acquire / Start / Open / Vote / Register`），按进程 `PID` 顺流排查是否因中途报错或条件分支遗漏导致一直未走到 `Release / Stop / Close / Unvote`。
2. **思路 ②【算力/网络/唤醒居高（CPU 线程高 / 发包高） $\rightarrow$ 查“报错死循环重试”】**
   - 用异常段 vs `Ref` 正常段做日志模板差分，重点抓只在异常段暴增数百次的周期刷屏词（如 `failed / retry / timeout / not ready / error`）。
3. **思路 ③【低深睡无长持锁 / 外设异常 $\rightarrow$ 查“状态机乒乓震荡”】**
   - 检索是否存在两个对立状态高频反复横跳（如 `Sleep <-> Wakeup`、`100% <-> 99%` 复充、`Connect <-> Disconnect`、`Attach <-> Detach`）。
4. **思路 ④【代理持锁（如系统代理锁）或 A 进程干等 $\rightarrow$ 查“跨进程上下游阻塞”】**
   - 不要只看表层代理进程 A，展开异常前后上下文，查 A 是否通过 IPC/Binder 向服务 B 发请求或持锁代办，顺藤摸瓜去查上游调用方或下游被等服务 B 的日志。
5. **思路 ⑤【灭屏或切后台后仍在跑前台重任务 $\rightarrow$ 查“状态拦截失效”】**
   - 对照灭屏节点（如 `ScreenOff`）或切后台/拔充节点，检查进程是否打印了阻止休眠/跳过暂停类日志（如 `skip pause / keep running / ignore freeze`）。

## 五、第四步：结案防幻觉“三问自检”与报告合并规则

### 🔒 结案前必问三句话（任意一条不通过则推翻重查）
1. **时间对得上吗？** 这条异常日志是否贯穿整个高耗电时段（或锁在开头申请后一直未释放）？如果几小时里只偶发报错 1 次，绝不是主因。
2. **硬件对得上吗？** 日志揭示的软件行为能否合理解释 `.db` 里耗电最高或漏电的硬件维度（如 `Display` 高刷、外设漏电、`CPU` 满频等）？
3. **正常段真的没有吗？** 当同库存在低耗 `Ref` 段时，确认该异常日志在 `Ref` 段中未同频疯狂打印（若 `Ref` 段也在狂打，通常只是无害背景噪音）。

### 多异常段汇总结论规则
- **整单唯一总结论（分开写“耗电判断”和“归因状态”）**：一份数据若检出多个待审切片，顶部只给 1 个整单总结论——只要任意一段存在异常，就判为 `耗电异常`（仅当所有高耗电段皆为合理使用且无明显无关异常拖累时，才判为 `符合正常使用场景`）；至于根因是不是已经坐实，用 `归因状态` 单独说明：证据链闭环填 `根因已确认`，若缺日志或缺底层表、只看出最大嫌疑项时，老实标为 `疑似对象` 并写明还缺什么证据，不要强行硬猜。
- **同因自动合并**：不同时间段若经核实为完全相同的元凶导致，合并为一个归因详情章节展示，仅列举时间段集合与合计数据，不重复刷屏。
