# 功耗审单 Skill 标准测试与验收手册

> **用途**：在内网完成 `scripts/` 代码编写与真实 `.db`/日志适配后，按本手册从“单步对账 $\rightarrow$ 工具单测 $\rightarrow$ 历史单盲测”逐关核对，快速找出算错数、漏抓真凶、误豁免或瞎编结论的问题。

---

## 零、测试前准备（先挑好样本）

不要一上来就拿没查明白的新单测试，先在手头挑出 **两批已结案、人工清楚标准答案的历史单**：
1. **对账基准单（1 单）**：挑 1 份你最熟悉、既有 `.db` 又有完整日志的典型问题单，用于第一关、第二关逐项核对数字；
2. **盲测验收包（6 类，共 6~8 单）**：覆盖不同边界情况（详见第三关表格），用于不提示答案的端到端盲测。

---

## 第一关：`.db` 切片与 4 列表对账（测 `stage1_db` + `stage2_evidence`）

用【对账基准单】单独运行阶段一、二脚本，拿输出结果与你平时用内部工具看的结果逐条核对：

### 1. 必查核对项（全部打勾才算过关）
- [ ] **切片边界准确**：充电时段、拔充电器后电压回落期（默认 `5 分钟`）已被剔除；切出的 `Target` 异常段起止时间与人工看的一致；若报障时间窗很短，未被直接丢弃漏检。
- [ ] **电池真实均流与掉电率一致**：脚本算出的 $I_{\text{real}}$（`mA`）和掉电率（`%/h`）与人工计算一致；若该单没有 `mAh` 只有电量百分比 `level %`，输出的均流必须带有 **`[估算值]`** 标记。
- [ ] **软件模拟覆盖率没算偏**：各器件模拟能量已先统一换算为 `mAs`（`1 mAh = 3600 mAs`、`1 uAh = 3.6 mAs`），且没有把同一器件的父子汇总行重复相加。
- [ ] **累加型字段没误用 `SUM`**：凡是开机以来递增的累计值（如累计持锁时长、累计唤醒次数、累计耗电），脚本算的都是**段末值减段初值**（中途重启已分段计算），没有直接按行 `SUM` 求和。
- [ ] **跨时间窗的时长已裁剪**：如果一条持锁或前台运行记录横跨切片起点或终点，脚本只计入了落在本切片内的时长，占比不会超过 `100%`。
- [ ] **头号嫌犯与双榜合并正确**：4 列对比表里排最前的硬件、应用、持锁、唤醒源与人工查出的一致；总占比不高但相比 `Ref` 暴增前 3 名的对象能以 `[突增入选]` 出现在表里，其余项合并为 `Others`。
- [ ] **缺失数据未乱填 `0`**：当 `Target` 或 `Ref` 段某项未采集、缺表或缺字段时，表格里显示的是 **`无数据`**，绝对不能填成 `0`（防止把未采集误判成从 `0` 暴增）。
- [ ] **案例库召回正常**：已知包名/锁名能精确召回对应旧卡片；把包名临时改成一个假名字时，仍能按超标槽位类别（如 `SQL_OFF_2` 持锁类）召回 2~3 张同类旧案例卡片。

### 2. 数字对不上时的快速排错表

| 看到的错误现象 | 通常是哪里写错了 |
| :--- | :--- |
| 均流 `mA` 或掉电率差了 1000 倍 / 3600 倍 | 时间戳单位（毫秒 `ms` vs 秒 `s`）没统一，或 `mAh` / `uAh` 转 `mAs` 漏乘系数。 |
| 持锁占比、CPU 占比算出来超过 `100%`（甚至几百 %） | 把开机累加字段直接 `SUM` 求和了，或者跨切片边界的起止时长没有按切片窗口截断。 |
| 软件模拟覆盖率总是只有个位数（如 `2%`） | 漏算了某几张大头硬件器件表（如 `Display` / `CPU`），或器件表能量单位没转成 `mAs`。 |
| 对照变化列（`Target - Ref`）出现大量假突增 | `Ref` 段没采到的数据被默认塞了 `0`，导致 `Target - 0` 全部虚高。 |

## 第二关：4 个查日志工具独立验证（测 `stage3_log`）

继续用【对账基准单】的日志目录，在命令行单独调用 4 个日志工具核对：

### 1. 必查核对项
- [ ] **时间窗截取准确**：传入 `.db` 异常段的起止时间，能准确捞出该时段内的 `hilog` 和 `kernel_log`，开头和结尾时间戳对得上。
- [ ] **包名转 `PID` 完整（`pid-trace`）**：输入异常包名，找出的 `PID` 列表与你在日志里手动搜的一致；若进程在异常段中途重启过，新旧 `PID` 都能找全。
- [ ] **异常/正常段差分有效（`diff`）**：能抓出异常段高频刷屏（如报错、重试、状态跳变）而在 `Ref` 段很少出现的日志模板；当传入 `Ref = 无` 时，工具能正常跳过差分或只统计异常段高频词，不报错。
- [ ] **搜索与上下文带行号（`search` & `context`）**：搜锁名或关键词能返回原始文件名和行号；拉取前后 35 行上下文内容完整，且面对几百 MB 大日志时流式读取不卡死、内存不暴涨。

### 2. 日志工具捞不到内容的排错表

| 看到的错误现象 | 通常是哪里写错了 |
| :--- | :--- |
| 按时间窗捞出来是 `0` 行 | ① 日志时间戳不带年份（如 `11-08 02:15:00`），代码转时间戳时默认成了 1970 年或当年年份不对；<br>② 跨零点（`23:50 ~ 00:30`）日期加一逻辑漏了；<br>③ `kernel_log` 只有开机秒数 `[12345.67]`，没和墙上时间基准对齐。 |
| 包名转 `PID` 找不到或漏日志 | 只匹配了进程创建那一刻的日志，但创建日志早在切片开始前就被冲掉了——需要同时从行首/行内自带 `PID` 与进程名关联的地方兜底提取。 |

## 第三关：6 类历史单端到端盲测（整体验收标准）

前两关通过后，拿准备好的 **6 类历史单**，**不提前告诉 AI 原因**，只给 `.db` + 日志路径跑完整审单，按下面标准验收报告：

| 序号 | 必测单据类型 | 验收通过标准（有一项不符则退回修规则或代码） |
| :--- | :--- | :--- |
| **1** | **已知明确软件 Bug 单**<br>（灭屏持锁/唤醒、亮屏高刷/后台陪跑各测 1~2 单） | - `耗电判断` 为 `耗电异常`，`归因状态` 为 `根因已确认`；<br>- 点名的包名/进程/锁名与人工结论完全一致；<br>- 报告贴出的 `.db` 占比数字和 2~4 行日志原文在原文件里真实可查，无编造。 |
| **2** | **正常重度使用单 + 复合异常单**<br>（如熄屏听歌/大流量真下载、亮屏打游戏，以及“前台打游戏但后台同时有云同步偷跑”） | - 纯正常重度使用单能判为 `符合正常使用场景` 豁免，不误报成 Bug；<br>- **关键防漏**：当主场景正常（如听歌/打游戏），但同时存在无关高耗电后台（`>= 15%`）、长持锁或异常唤醒时，**不能整段一刀切豁免**，必须指出异常后台/持锁项。 |
| **3** | **先后切换多个应用 vs 真分屏单**<br>（如前半小时用应用 A、后半小时切应用 B，各自前台占比都 `> 30%`） | - 先后切换使用 A 和 B 时，**绝不能误打标为 `[平板分屏/多窗并发模式]`**；<br>- 只有时间区间真正重叠、有窗口状态标记或前台总时长明显超切片（如 `> 1.2 × Δt`）才打分屏标。 |
| **4** | **只有 `.db` 无日志（或关键日志被冲掉）的单** | - 报告必须将结论拆开写：**`耗电判断：耗电异常` + `归因状态：疑似对象` + 写明还缺什么证据**（如“尚缺释放锁日志”）；<br>- **严禁**在没日志铁证时硬猜成 `根因已确认`。 |
| **5** | **缺底层表 / 全库全程漏电（或仅 1 段 `Ref = 无`）的单** | - 删掉线程表或外设表后运行，脚本**不报错中断**，能输出跳过说明与线下 `hiperf` 补抓提示；<br>- 当 `Ref` 同样高耗电或 `Ref = 无`（导致第 ③ 列 `Diff ≈ 0`）时，AI 能看第 ① 列断层霸榜项 + 跨表同名共振锁定嫌犯。 |
| **6** | **软件模拟覆盖率 `< 35%` 的单** | - 遇到 `< 35%` 时，先自检不是因为缺器件表或单位漏换算成 `mAs`；<br>- 排除少算漏算后，才标记“存在未解释耗电”并排查手写笔复充/键盘/OTG 等外设盲区或建议硬件实测。 |

## 第四关：固化回归样本（防以后改坏）

盲测全部通过后，从上面 6 类单子里各截取一份**脱敏微缩样本**（只保留必要时间窗的 `.db` 记录与几十行关键日志，去掉敏感信息），放进 `tests/fixtures/`：
- 以后每次调整 [thresholds.json](../assets/config/thresholds.json)、修改 SQL 或升级脚本后，先把这几份固定样本重跑一遍；
- 确认老单子的“异常段切分、4 列表 Top 嫌犯、最终耗电判断与归因状态”没有退化，再正式合入使用。
